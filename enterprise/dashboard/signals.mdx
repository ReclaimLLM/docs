The Signals tab (`/enterprise/orgs/{org_id}/signals`) helps organization administrators find recurring AI-work patterns and investigate deterministic anomaly findings with the sessions behind them.

<Warning>
  Signals are investigation aids, not employee-performance scores or automatic policy violations. Review the linked evidence and the interpretation guardrails before acting.
</Warning>

## Date range

The page opens to the last 30 days. Set **From** and **To** dates or select **Last 30 days** to reset the range.

The range applies slightly differently to each section:

- The Signals matrix includes signal periods written during the selected window.
- Anomaly reports include findings whose latest occurrence falls inside the selected window.
- The selected **To** day is included; the frontend sends the following day as the API's exclusive upper bound.

## Signals matrix

Signals group recurring patterns by team and project so you can see where enablement, policy, or durable project context will have the most leverage.

Each populated cell shows:

- **Projected tokens per week** when the signal has an estimate.
- **Open signal count** when projected-token coverage is unavailable.
- A stronger color for a larger projected opportunity or open count within that matrix.
- Linked evidence sessions when the cell is clickable.

The page provides three views:

- **P4 · Users with waiting sessions** — sessions, qualifying wait events, maximum and total wait, the worst session, and a direct evidence-session link.
- **Teams × patterns** — concentration across a team, best used for shared conventions, policy, and enablement rather than individual performance review.
- **Projects × patterns** — concentration by codebase. Projects with the same configured display name are merged into one row.

For P4 project cells, the value is the number of affected sessions. Elapsed wait time is not converted into token savings.

### How to investigate a Signal

1. **Find concentration** — start with the darkest or largest populated cells.
2. **Choose the owner** — team rows usually point to a policy or enablement owner; project rows point to a codebase owner; P4 user rows identify exact sessions to review.
3. **Open evidence** — inspect linked sessions before deciding whether the pattern needs a change.
4. **Read the pattern details** — select a code in **What the pattern codes mean** for examples, recommended admin actions, and interpretation guardrails.

### Pattern catalog

| Code | Pattern | What it identifies | Typical admin action |
| --- | --- | --- | --- |
| **P1** | Restart churn | Work repeatedly restarts on the same project instead of continuing from a useful handoff. | Improve handoffs or project instructions. |
| **P2** | Groundhog files | The same files are re-read across sessions or contributors to recover context that could be documented once. | Add durable project context or use `file_brief`. |
| **P3** | Exploration without landing | A session spends heavily on searching and reading but produces few or no edits. | Tighten task briefs and entry points without penalizing legitimate discovery. |
| **P4** | Session idle gaps | The next user prompt repeatedly arrives after the configured wait threshold. | Review interruption and handoff patterns; do not use this as activity monitoring. |
| **P5** | Session bloat | Sessions run beyond the member's normal completion point while context keeps growing. | Define sensible handoff or session-splitting guidance. |
| **P6** | Compression policy drift | Supported hooks remain off or observe-only when the organization requires enforcement. | Check policy sync and stale hook installations before assuming intent. |
| **P7** | Project onboarding cost | New contributors use materially more tokens than veterans on comparable project work. | Build or improve a project context pack. |
| **P8** | Cross-team duplicated work | Separate teams repeat substantially similar work without finding or reusing the earlier result. | Make the earlier work or artifact discoverable. |
| **P9** | Context-weight burn | A session carries much more cached context through each tool call than the member's normal baseline. | Split, hand off, or delegate unusually heavy sessions. |
| **P10** | Model–task mismatch | A costly model is used where comparable work is routinely completed with a lighter model. | Set targeted model-selection guidance instead of blocking premium models globally. |

### Monthly CSV report

Select **Export YYYY-MM CSV** to download the current month's organization-, team-, and project-scoped Signals. The report includes the period, scope, pattern, status, evidence count, idle minutes, measured opportunity tokens, and projected tokens. Member identities are not included.

## Anomaly reports

Anomaly reports are nightly deterministic checks over completed session data. They are not AI-generated classifications.

The header shows the number of open findings and the number currently marked high or critical. Filter the list by:

- Status: open, new, acknowledged, resolved, dismissed, or all.
- Severity: warning, high, critical, or all.
- Detector.
- The page-level date range.

Each finding shows its detector code, severity, status, subject, latest occurrence, occurrence count, evidence summary, and linked sessions when available.

### Detectors

| Code | Detector | What it checks | Interpretation guardrail |
| --- | --- | --- | --- |
| **AD-001** | Usage baseline deviation | Daily session or token volume materially above that member's own rolling history. | It compares each member with themselves, not with an organization-wide threshold. Missing or inconsistent coverage does not fire a finding. |
| **AD-002** | New technology fingerprint | A first-seen combination of dependencies, imports, manifests, tools, or project activity. | Novelty is not an access or policy violation. Confirm a legitimate new project or role change before escalating. |
| **AD-003** | Runaway or looping session | Repeated failures, identical retries, failed build/test loops, unusually high tool-call volume, abnormal duration, or related stuck-workflow behavior. | The finding indicates possible operational waste, not malicious behavior. Relative checks need history; exact retry loops can fire without a baseline. |
| **AD-004** | Sensitive file access | Sessions where an AI agent read or wrote `.env`, `.envrc`, credential, or private-key files — via native read tools or shell commands. | Accessing env files is not inherently prohibited. The finding indicates the session touched sensitive file paths; whether secrets reached the model depends on whether hook DLP was active for that session. |
| **AD-005** | Proxy operation volume spike | A proxy operation's daily session volume is materially above the organization's own recent history for that operation. | A spike indicates unusual volume, not malicious use. Requires sufficient historical activity to establish a baseline before it can fire. |
| **AD-006** | New proxy operation | A canonical proxy operation title appears for the first time in the organization's recorded history. | First-seen is not inherently unsafe. Verify that the new operation belongs to an approved integration or workflow before escalating. |

#### AD-001 — Usage baseline deviation

Daily session or token activity is materially above that member's own rolling history. The detector compares each person with themselves over the previous 14 completed days using a guarded exponentially weighted baseline. A finding requires three conditions to align: a strong statistical deviation, a meaningful ratio above the member's own baseline, and an absolute increase floor. Missing or inconsistent provider-reported coverage blocks the finding rather than producing a misleading result.

**Typical next steps:** Confirm whether the increase matches planned work or an expected shift in role. Open the linked sessions to determine whether the volume is legitimate before deciding on any action.

#### AD-002 — New technology fingerprint

A session contains a first-seen combination of dependencies, imports, manifests, tools, or project activity relative to that member's prior 90-day history. A single new extension or provider is not enough; the detector requires a meaningful combination, such as a new package ecosystem together with a first-seen dependency, or a new project root with a new command family.

**Typical next steps:** Check whether the technology belongs to a legitimate new project or role change. First-seen activity is not evidence of a policy violation.

#### AD-003 — Runaway or looping session

A session shows repeated failures, identical retries, or activity far above the member's normal session behavior. Deterministic sub-signals include: consecutive identical-input errors on the same tool, repeated failing operations on the same file, build or test failures without an intervening edit, abnormal tool-call volume, and abnormal duration. Severity escalates when two independent sub-signals fire together.

**Typical next steps:** Open the evidence session and determine whether an agent configuration, failing command, or workflow needs intervention. The finding indicates operational waste or a stuck workflow, not malicious behavior.

#### AD-004 — Sensitive file access

Sessions where an AI agent read, wrote, or referenced `.env`, `.env.*`, `*.env`, `.envrc`, certificate, or private-key files. Detection covers three surfaces:

- **Direct tool access** — native Read and Write tool calls where `primary_file_path` or `file_paths[]` match a sensitive-file pattern.
- **Shell command access** — paths extracted from `cat`, `head`, `tail`, `sed`, and `rg` commands, covering the most common real-world leak path.
- **Code and script mentions** — text in agent-written files or tool outputs that references sensitive files: `load_dotenv(".env.production")`, `open(".env", "r")`, `source .env && ...`, or similar constructs. This surface catches the case where the model writes a temporary Python or Bash script that reads or modifies an env file — a vector that never passes through a tool-call hook boundary and is therefore outside the standard hook DLP guarantee.

Evidence records the access type (`read`, `write`, `shell_read`, `code_mention`) and whether hook DLP was active per tool call — never the actual file content or secret values.

Severity tiers:

- **Warning** — one or more sessions with a sensitive file read or `code_mention`.
- **High** — at least one session wrote to a sensitive file path or the code mention involves a write operation.
- **Critical** — multiple sessions have env-file activity and at least one had no DLP coverage, indicating a gap where secrets or a script referencing them may have reached an external model provider.

**Typical next steps:** Check the access type in evidence. For `code_mention`, open the linked session and determine whether the script was executed and whether that execution had DLP coverage. For direct or shell reads with `was_redacted: false`, determine whether secrets were transmitted to an external provider.

#### AD-005 — Proxy operation volume spike

A canonical proxy operation's daily session volume is materially above the organization's own recent daily history for that operation. The detector requires sufficient active-day history before it can fire, and compares the operation with its own baseline rather than with a global threshold. Evidence contains the operation title, bounded statistics, and a limited number of session identifiers — not request bodies, prompts, or provider credentials.

**Typical next steps:** Confirm whether the operation's increase is expected, then inspect the linked sessions for unexpected callers or inputs.

#### AD-006 — New proxy operation

A canonical proxy operation title appears for the first time in the organization's recent history, compared against the preceding 90 days of labeled activity. A sufficient baseline of prior labeled sessions is required before a title is treated as genuinely new.

**Typical next steps:** Verify that the new operation belongs to an approved integration or workflow. First-seen title novelty is an invitation to verify, not evidence of a policy violation.

### Finding status workflow

- **Acknowledge** a new finding when it is under review.
- **Resolve** it when the relevant work or remediation is complete.
- **Dismiss** it when the finding is expected behavior or a false positive.
- Resolved and dismissed findings are closed and cannot transition to another status.

## Email alerts & notification cadence

Administrators can configure automated email notifications for developer workflow signals and deterministic security anomalies.

Click **Configure Email Alerts & Cadence** in the top-right header of the Signals tab to open the configuration modal directly on the page, or navigate to Organization **Settings** (`/enterprise/orgs/{org_id}/settings`) under **Email Alerts & Cadence**.

### Delivery cadences

| Alert type | Default cadence | Supported options | Trigger conditions |
| --- | --- | --- | --- |
| **Security Alerts (P0)** | Immediate (Real-time) | Immediate, Daily morning digest, Off | Critical findings or sensitive file access (**AD-004** direct tool, shell, or script mentions without DLP). Dispatched immediately upon detection. |
| **Anomaly Digest** | Daily (08:00 UTC) | Daily, Weekly (Monday 08:00 UTC), Off | Consolidated summary of deterministic findings across rolling 24-hour windows. |
| **Signals Digest** | Weekly (Monday 08:00 UTC) | Weekly, Daily, Off | Aggregated engineering efficiency patterns and coaching recommendations (**P1–P10**). |

### Configuration options

- **Minimum severity threshold** — filter out lower-severity warnings from email dispatch (`Warning, High & Critical (All)`, `High & Critical only`, or `Critical only`). Findings below the selected threshold remain visible in the dashboard and audit log but do not generate emails.
- **Included anomaly detectors** — toggle individual detectors (**AD-001** through **AD-006**) to match your team's current focus. For example, if engineering teams are actively exploring new frameworks, you can temporarily exclude **AD-002 (New technology fingerprint)** while keeping **AD-004 (Sensitive file access)** active.
- **Included workflow signals** — toggle individual signal codes (**P1** through **P10**) to tailor the weekly digest.
- **Recipient inboxes** — provide a comma-separated list of target email addresses (e.g., `security@company.com, leads@company.com`). If left blank, notifications default to all organization administrators.
- **Excluded projects / sandboxes** — specify comma-separated project names or path prefixes (e.g., `scratch, test-sandbox, playground`) to suppress alerts from experimental or throwaway environments.

### Testing email delivery

You can test mailbox reception and email rendering without waiting for scheduled batches:

1. Click **Configure Email Alerts & Cadence** in the Signals header.
2. Under **Test Email Delivery**, select **Test P0 Alert** (to preview an immediate sensitive file alert) or **Test Daily Digest** (to preview a rolling 24-hour anomaly report).
3. The server dispatches a sample email to the first configured recipient inbox (or your current admin account if none is specified).

## Who sees it

The Signals tab, organization matrix, anomaly findings, status actions, and monthly CSV export are administrator-only. The navigation hides this tab from team leads and developers, and the backend enforces the same boundary.

<Note>
  Empty matrices or report lists do not mean collection is broken. Signals require eligible completed-session evidence, and anomaly detectors may require sufficient historical coverage before they can fire.
</Note>

For the surrounding operating model, see [Enterprise Observability](/enterprise/observability). Use [Sessions](/enterprise/dashboard/sessions) to continue a broader investigation and [Tokens](/enterprise/dashboard/tokens) for organization-wide consumption and measured context reduction.
